Create the writing sample collection specification document. This is a dedicated deliverable addressing Success Criterion 3 and DATA-04 (writing sample collection for academic discourse analysis).

**Document structure:**

**1. Purpose and Scope**
- Purpose: define how writing artifacts are captured, stored, and made available for analysis
- Scope: all student-authored text submitted through the learning analytics system (writing tasks, forum posts, peer review feedback)
- Key downstream consumer: Phase 5 CoP academic discourse adoption metric, which needs writing artifacts to detect vocabulary markers, citation patterns, and argument structure
- DPIA reference: link to the "Writing Sample Submissions" section in governance/dpia/01-processing-description.md
- Privacy constraint: writing artifacts are Personal Information under POPIA; access governed by the access control matrix (student and assigned tutor only; teaching team has NO access to individual writing samples)

**2. Capture Rules**
- **When:** Capture on submit only (locked decision). No periodic auto-saves, no keystroke logging.
- **What:** Full text of the submitted artifact at each submission event (draft or final)
- **Draft tracking:** Each submission generates a separate xAPI statement with incrementing draft-number. Draft 1 is the first submission, draft 2 is a revision, etc. The system does NOT compute diffs between drafts -- each submission is a complete snapshot.
- **Forum posts:** Forum post text is captured in the forum-post-created and forum-reply-posted statements via result.response. These are ALSO writing artifacts for discourse analysis purposes, but use the discussion templates rather than the writing-submitted template.
- **Peer review feedback:** Feedback text is captured in the peer-review-submitted statement via the feedback-text result extension. This is a writing artifact for CoP analysis.

**3. Storage Strategy: Inline vs External Reference**
- **Threshold:** 1000 characters (locked decision from 02-CONTEXT.md)
- **Inline (text <= 1000 chars):** Text stored in `result.response` field of the xAPI statement. Applies to: forum posts, short reflections, peer review feedback, short paragraphs.
  - Advantage: self-contained statement, works offline, no external dependency
  - xAPI compliance: `result.response` is a standard field for capturing learner input
- **External reference (text > 1000 chars):** Text stored in an external artifact store. The xAPI statement includes:
  - `result.extensions["artifact-url"]`: URL/ID reference to the stored artifact
  - `result.extensions["artifact-content-type"]`: MIME type (typically "text/plain" or "text/markdown")
  - `result.response` is OMITTED (not duplicated) to avoid bloating the LRS
  - Applies to: essays, reports, long reflections, annotated bibliographies
- **Artifact store requirements** (specification level -- implementation details deferred):
  - Unique artifact ID per submission (UUID recommended)
  - Immutable storage -- once stored, an artifact is not modified (new draft = new artifact)
  - Access control: must enforce same access rules as the LRS (student + assigned tutor only)
  - Retention: follows the same data lifecycle as the xAPI statements (deletion at end of academic year)
  - Format: plain text or markdown; no binary formats for writing artifacts

**4. Required Metadata (Writing Extensions)**
Every writing-submitted statement MUST include:
| Extension | Required/Recommended | Description | Computed By |
|-----------|---------------------|-------------|-------------|
| word-count | Required | Number of words | Client-side at submission time |
| draft-number | Required | Draft iteration (1, 2, 3...) | Client-side, incremented per task |
| assignment-type | Required | Type of writing task | From assignment configuration |
| paragraph-count | Recommended | Number of paragraphs | Client-side at submission time |
| citation-count | Recommended | Number of citations/references | Client-side, heuristic detection (e.g., count parenthetical references, bibliography entries) |
| time-spent | Recommended | ISO 8601 duration on task | Client-side timer (start from task open to submit) |
| prompt-topic | Recommended | Writing prompt or topic | From assignment configuration |
| artifact-url | Conditional | External artifact reference | Generated at storage time (external artifacts only) |
| artifact-content-type | Conditional | MIME type of external artifact | Set at storage time (external artifacts only) |

"Required" = MUST be present in every writing-submitted statement (validated by JSON Schema).
"Recommended" = SHOULD be present; absence is tolerated but reduces analysis capability.
"Conditional" = Required only for external reference artifacts (text > 1000 chars).

**5. Computation Rules for Metadata**
- **Word count:** Split text by whitespace, count tokens. Exclude empty tokens. Language-agnostic (works for English and code-switched text).
- **Paragraph count:** Count blocks separated by double newlines or `\n\n`. Minimum 1 paragraph for any non-empty text.
- **Citation count:** Heuristic. Count: (1) parenthetical references matching patterns like `(Author, Year)` or `(Author Year)`, (2) numbered references like `[1]` or `[12]`, (3) entries in a "References" or "Bibliography" section if detected. This is an approximation -- precise citation parsing is a Phase 5 concern. Document that the count is heuristic and may under/over-count.
- **Time spent:** Duration from first interaction with the writing task (page load / task open) to submit button click. If the student navigates away and returns, time is cumulative (timer pauses on navigate-away, resumes on return). Offline time is counted if the client tracks it locally. Format: ISO 8601 duration (e.g., "PT25M", "PT2H15M").
- **Draft number:** Sequential per writing task per student. First submission = 1, each resubmission increments. The client is responsible for tracking draft sequence. If a student submits, then submits again for the same task, draft-number goes from 1 to 2.

**6. Offline Considerations**
- Writing submissions captured offline are queued as self-contained xAPI statements (with inline text for short artifacts)
- For external reference artifacts captured offline: the artifact text is stored locally and queued for upload. The xAPI statement is queued with a provisional artifact-url (local reference). On sync, the artifact is uploaded to the external store, and the statement's artifact-url is updated to the permanent URL before LRS submission.
- Phase 3 (Offline Data Pipeline) will specify the exact queuing and sync mechanism. This spec defines the data model requirements that the pipeline must satisfy.

**7. Academic Discourse Analysis Support**
This section documents how the writing artifact data supports Phase 5 CoP metrics:
- **Vocabulary marker detection:** Requires access to the full text (inline or via artifact-url). Word count and citation count provide structural indicators. The actual lexical analysis (detecting academic register, hedging language, discipline-specific terminology) is a Phase 5 concern, not defined here.
- **Citation pattern analysis:** citation-count provides a rough indicator. Detailed citation analysis (style consistency, source diversity, self-citation vs external) requires the full text and is deferred to Phase 5.
- **Argument structure indicators:** paragraph-count provides a structural proxy (more paragraphs may indicate more structured argument). Actual argument analysis is deferred to Phase 5.
- **Draft progression analysis:** The combination of draft-number, word-count, and citation-count across sequential drafts for the same assignment enables trajectory analysis (is the student's writing improving over revisions?).
- **Cross-context transfer:** Writing artifacts from different assignment-types and modules can be compared to detect transfer of academic literacy skills. The assignment-type and module context (from the session grouping) enable this cross-referencing.

**8. Data Flow Diagram** (text-based)
```
Student writes text
       |
       v

       |
       v
Text length <= 1000 chars?
      / \
    Yes   No

  Inline  Store in artifact store
  in      Get artifact-url
  result. |
  response|
     \   /
      \ /
       v
Build xAPI statement (writing-submitted template)
       |
       v
Queue for LRS submission (online or offline)
```

Update the profile JSON-LD to populate the `patterns` array with statement patterns that define valid event sequences.

**xAPI Profile patterns use three pattern types:**
- `sequence`: ordered list of template/pattern references (events happen in this order)
- `alternates`: one of the listed templates/patterns occurs
- `optional`: the referenced template/pattern may or may not occur
- `oneOrMore`: the referenced template/pattern occurs one or more times
- `zeroOrMore`: the referenced template/pattern occurs zero or more times

**Patterns to define:**

1. **Session Lifecycle Pattern** (`session-lifecycle`)
   - `type`: "Pattern"
   - `primary`: true (this is a top-level pattern)
   - `definition`: "A complete learning session from login to logout, containing zero or more learning activities."
   - Structure: `sequence` of:
     1. `session-opened` template
     2. `zeroOrMore` of `session-activity` pattern (defined below)
     3. `session-closed` template (optional -- session may end without explicit logout due to timeout/connectivity loss)

2. **Session Activity Pattern** (`session-activity`)
   - `primary`: false (sub-pattern)
   - `definition`: "Any learning activity that occurs within a session."
   - Structure: `alternates` of:
     - `page-viewed` template
     - `module-navigated` template
     - `reading-activity` pattern
     - `quiz-activity` pattern
     - `writing-submitted` template
     - `discussion-activity` pattern
     - `peer-review-submitted` template
     - `help-seeking-activity` pattern
     - `module-completed` template
     - `course-progressed` template
     - `self-report-submitted` template

3. **Reading Activity Pattern** (`reading-activity`)
   - `primary`: false
   - `definition`: "A reading interaction: view a section, optionally complete it."
   - Structure: `sequence` of:
     1. `reading-section-viewed` template
     2. `reading-section-completed` template (optional)

4. **Quiz Activity Pattern** (`quiz-activity`)
   - `primary`: false
   - `definition`: "A quiz attempt workflow: attempt, answer questions, then complete with pass/fail outcome."
   - Structure: `sequence` of:
     1. `quiz-attempted` template
     2. `oneOrMore` of `question-answered` template
     3. `quiz-outcome` pattern (alternates: quiz-completed, quiz-passed, quiz-failed)

5. **Quiz Outcome Pattern** (`quiz-outcome`)
   - `primary`: false
   - `definition`: "The outcome of a quiz attempt."
   - Structure: `alternates` of:
     - `quiz-completed` template
     - `quiz-passed` template
     - `quiz-failed` template

6. **Discussion Activity Pattern** (`discussion-activity`)
   - `primary`: false
   - `definition`: "A discussion forum interaction: view thread, create post, or reply."
   - Structure: `alternates` of:
     - `thread-viewed` template
     - `forum-post-created` template
     - `forum-reply-posted` template

7. **Help-Seeking Activity Pattern** (`help-seeking-activity`)
   - `primary`: false
   - `definition`: "A help-seeking interaction: request help, access a help resource, or request an extension."
   - Structure: `alternates` of:
     - `help-requested` template
     - `help-resource-accessed` template
     - `extension-requested` template

**Pattern format in JSON-LD (xAPI Profile spec):**
```json
{
  "id": "https://w3id.org/xapi/aclit/v1/patterns/session-lifecycle",
  "type": "Pattern",
  "primary": true,
  "inScheme": "https://w3id.org/xapi/aclit/v1",
  "prefLabel": {"en": "Session Lifecycle"},
  "definition": {"en": "A complete learning session..."},
  "sequence": [
    "https://w3id.org/xapi/aclit/v1/templates/session-opened",
    "https://w3id.org/xapi/aclit/v1/patterns/session-activities",
    "https://w3id.org/xapi/aclit/v1/patterns/session-close-optional"
  ]
}
```

For composition patterns (zeroOrMore, oneOrMore, optional), they are separate Pattern objects:
```json
{
  "id": "https://w3id.org/xapi/aclit/v1/patterns/session-activities",
  "type": "Pattern",
  "primary": false,
  "inScheme": "https://w3id.org/xapi/aclit/v1",
  "zeroOrMore": "https://w3id.org/xapi/aclit/v1/patterns/session-activity"
}
```

Ensure the profile remains valid JSON after adding patterns. The patterns array should contain all pattern definitions (both primary and sub-patterns).
