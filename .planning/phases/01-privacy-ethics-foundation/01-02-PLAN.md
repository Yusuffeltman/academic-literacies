  <action>
Create governance/retention/ directory and the data lifecycle specification.

**Document structure:**

**1. Scope and Principles**
- Covers all personal information processed by the learning analytics system
- Governed by POPIA Section 14 (retention and restriction of records)
- Core principle: data retained only as long as necessary for the specific pedagogical purpose
- Locked decision: uniform retention period for all data types (simplicity)

**2. Data Categories**
Define each data category with:
- Category name (e.g., "LMS Interaction Events", "Writing Samples", "Self-Report Responses", "Quiz/Assessment Records", "Discussion Forum Activity", "Session Metadata", "Derived Metrics/Scores")
- Description of what's included
- Classification: Personal Information / Special Personal Information / De-identified
- Note: all categories are Personal Information under POPIA; derived metrics computed from personal data retain their classification until aggregated beyond re-identification

**3. Retention Rules**
For each data category:
- Retention period: End of academic year (locked decision)
- Retention trigger: Date of collection
- Deletion trigger: End of academic year in which the data was collected (define "end of academic year" precisely -- e.g., 31 January of the following year to allow for supplementary exams and final grade processing)
- Legal basis for retention: POPIA Section 14 -- retention for the period necessary to achieve the purpose (pedagogical support during the course)

**4. Deletion Procedures**
This is critical (research Pitfall 6 -- retention without deletion procedure is a common failure). For each step:
- **Deletion trigger event:** End of academic year date reached
- **Responsible role:** System Administrator (role, not individual)
- **Pre-deletion checklist:**
  - All grades finalized
  - No pending data access requests
  - No pending objection proceedings
  - Export period offered to students (at least 30 days notice before deletion)
- **Deletion process:**
  - Individual-level data: permanently deleted from production database
  - Backup data: deleted from backups within 30 days of production deletion (or next backup rotation cycle)
  - Derived/aggregated statistics: RETAINED -- once aggregated beyond individual identification, data is no longer personal information (research Open Question 4 recommendation)
  - Audit logs of data access: retained for 1 year beyond data deletion (for accountability under POPIA Section 8)
- **Verification:** Deletion confirmation report generated and retained
- **Student notification:** Students notified that deletion has occurred (or will occur) via institutional communication channel

**5. Student-Initiated Deletion**
- Available AFTER course ends (locked decision: no mid-course deletion)
- Process: written request to Information Officer
- Timeline: deletion within 30 days of verified request
- Scope: all individual-level data; aggregated statistics retained
- Confirmation: written confirmation sent to student
- Note: during the course, students may exercise objection rights (Section 11(3)) which stops further processing but does not trigger deletion

**6. Exceptions and Edge Cases**
- Student who withdraws from course mid-year: data retained until end of academic year, then deleted per standard process. Student may request early deletion after withdrawal.
- Supplementary exams: retention period accounts for supplementary exam period (hence January 31 cutoff, not December)
- Legal hold: if data is subject to legal proceedings, retention extends until proceedings conclude (POPIA Section 14(2))

Create governance/access-control/ directory and the access control matrix document.

**Document structure:**

**1. Overview and Principles**
- Purpose: define exactly which data each audience role can access
- Design principle: explainable to students in plain language (locked decision)
- Four roles: Student, Assigned Tutor, Teaching Team, System Administrator
- Default posture: no access unless explicitly granted in this matrix

**2. Role Definitions**
Define each role precisely:
- **Student:** The individual data subject. Sees only their OWN data. Cannot see other students' data in any form.
- **Assigned Tutor:** The tutor assigned to a specific student via a fixed mapping. Sees data for their assigned students ONLY. Cannot see students assigned to other tutors.
- **Teaching Team:** Course coordinator and academic staff responsible for the course as a whole. Sees AGGREGATED cohort data only. Cannot see individual student data. Cannot identify individual students from aggregated views.
- **System Administrator:** Technical role responsible for system operation. Has technical access to all data for maintenance and support purposes. Does not use data for pedagogical decisions. Access is logged and auditable.

**3. Access Control Matrix**
Create the matrix table from the research document (Pattern 2), expanded with all data categories from the retention spec:

| Data Category | Student (own data) | Assigned Tutor | Teaching Team | System Admin |
|---|---|---|---|---|
| Engagement metrics (session frequency, duration, completion rates) | Read | Read | Aggregated only | Technical access |
| Performance trends (quiz scores, writing quality progression) | Read | Read | Aggregated only | Technical access |
| CoP indicators (participation trajectory, discourse adoption, peer interaction, transfer) | Read | Read | Aggregated only | Technical access |
| SDL indicators (scaffolding dependence, self-regulation, calibration, help-seeking) | Read | Read | Aggregated only | Technical access |
| Self-report responses (confidence, goals, strategies) | Read | Read | Aggregated only | Technical access |
| Writing samples | Read | Read | No access | Technical access |
| Discussion forum posts (content) | Read (own) | Read (assigned students) | No access | Technical access |
| Raw event logs | No access | No access | No access | Technical access |
| Early warning flags | Read (own) | Read (assigned students) | Aggregated counts only | Technical access |
| Learning plan records | Read (own) | Read/Write (assigned students) | No access | Technical access |

**4. Aggregation Rules**
- "Aggregated only" means: statistical summaries (mean, median, distribution) computed across a GROUP of students
- Minimum group size: 10 students (from research recommendation; prevents re-identification in small cohorts)
- Cell suppression: if a filtered view (e.g., by demographic) produces a group smaller than 10, the cell is suppressed/redacted
- No drill-down: teaching team cannot click through aggregated data to reach individual records
- Aggregation applies to ALL data categories marked "Aggregated only" -- no exceptions

**5. Tutor-Student Mapping Rules**
- Mapping is fixed assignment (locked decision): each student has exactly one designated tutor
- Mapping is maintained by teaching team / course administration
- Tutor access is scoped strictly to assigned students
- If a student is reassigned to a different tutor, the previous tutor's access is revoked immediately
- Tutor cannot request access to non-assigned students

**6. Data Presentation Rules**
For student-facing views:
- Growth-focused framing: compare student to their OWN past performance, never to classmates (locked decision)
- No percentile rankings, no cohort position indicators
- No data that reveals other students' performance even indirectly

For tutor-facing views:
- Individual student data presented in context of that student's trajectory
- Cohort context available only as aggregated benchmarks (e.g., "cohort median" not individual comparisons)

**7. Plain Language Summary**
Include a section written in plain language suitable for inclusion in a student-facing privacy notice:
"As a student, you can see: [list]. Your tutor can see: [list]. The teaching team can see: [list]. Nobody else can see your individual data."
